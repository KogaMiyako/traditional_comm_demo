# 通信基础与“内容2”工作指南

## 面向零基础：理解通信过程、传统通信基线与性能记录

**适用任务：**语义通信 Demo 的“内容2：传统通信模型搭建”

这份指南只讲你当前任务中会真正遇到的概念。先理解数据怎么走，再理解为什么要记录这些指标，最后把工作拆成可以执行的程序和联调事项。

> **先记住一句话：**
>
> 你的任务不是重新发明通信系统，而是做一条传统通信基线：把同一张图片或同一段视频按 JPEG/H.264 等常规方式编码、传输、解码，再记录数据量、时延、质量和计算资源，和语义通信进行公平对比。

|---|---|---|
| 内容1 | 定义任务模式、数据集、对比指标、计算状态、信道条件和语义模型架构。 | 你需要沿用这些定义，不能单独换一套测试标准。 |
| 内容2 | 搭建传统通信模型并记录性能。 | 这是你的核心任务。 |
| 内容3 | 整合整个课题二 Demo，并对接其他课题。 | 你要把传统通信结果交给整合人员展示。 |
| 课题一 | 任务控制、状态采集、Web 展示和总体联调。 | 负责页面和设备状态，你提供接口和结果。 |
| 课题二 | 提供可运行的语义算法、模型和输入输出接口。 | 它是语义通信一侧，不是你的传统编码模块。 |
| 课题三 | 提供通信硬件、链路接入、SNR 设置和传输统计。 | 你使用它提供的链路，不必自行模拟完整硬件。 |
| 课题四 | 参与演示验证和后续平台接口确认。 | 属于验证与平台衔接。 |

## 2. “通信”到底是在做什么

最简单地说，通信就是：发送端把信息变成适合传输的形式，通过一条链路送出去，接收端再把它还原成可使用的结果。图片、视频、文字都可以看成要传输的信息。

可以把它类比成寄快递：原始图片像要寄的物品；编码像打包；数据包像一个个快递箱；通信链路像运输路线；解码像拆包；接收端最终得到图片或任务结果。

| 阶段 | 通俗解释 | 你的传统通信实现 |
|---|---|---|
| 输入 | 要发送的原始内容。 | 图片文件或视频文件。 |
| 编码 | 把内容压缩、转换成更适合传输的数据。 | 图片使用 JPEG 等，视频使用 H.264 等。 |
| 封装/分包 | 把较大的数据切成可以在网络中传输的小块。 | 按照课题三的接口或协议发送。 |
| 链路传输 | 数据经过 Wi-Fi、5G 或有线链路。 | 课题三提供链路和传输统计。 |
| 重组/解码 | 接收端把小块数据拼起来并还原内容。 | 数据重组后进行 JPEG/H.264 解码。 |
| 输出 | 用户或任务模型真正使用的结果。 | 重建图片/视频，或运行同一个任务模型。 |

## 3. 你的传统通信链路怎么走

Word 方案给出的传统通信路径可以理解为下面六步。你要做的程序，至少要能把这六步完整跑通。

| 步骤 | 发生了什么 | 要留下什么记录 |
|---|---|---|
| 1. 选择输入 | 选择一张图片或一段视频，并确定本轮任务。 | 样本名称、文件大小、分辨率、视频时长、任务类型。 |
| 2. 常规编码 | 把原始内容变成 JPEG、H.264 等编码载荷。 | 编码格式、质量参数、编码后字节数、编码耗时。 |
| 3. 发送传输 | 把编码载荷交给课题三的通信链路。 | 链路类型、SNR、发送时间、实际传输字节数。 |
| 4. 接收重组 | 接收端收集数据包，并恢复完整编码载荷。 | 接收时间、丢包/误码、重传情况。 |
| 5. 常规解码 | 将编码载荷恢复成图片帧或视频帧。 | 解码耗时、是否成功、输出文件。 |
| 6. 形成结果 | 输出重建内容，或把内容交给任务模型。 | 端到端时延、质量指标、任务指标、设备状态。 |

**传统通信的核心链路：**

```text
图片/视频 -> JPEG/H.264 编码 -> 分包 -> 通信链路 -> 重组 -> 解码 -> 重建结果/任务结果
```

## 4. JPEG、H.264 和“编码”是什么意思

编码不是加密。编码主要是把数据变得更适合存储和传输，通常会减少数据量。解码就是把编码后的数据恢复成图片或视频。

| 名词 | 是什么 | 在你的任务中怎么理解 |
|---|---|---|
| JPEG | 常见的图片压缩编码格式。 | 可以把一张原始图片编码成 JPEG 文件后传输。压缩质量越高，通常文件越大、图像损失越小。 |
| H.264 | 常见的视频编码标准。 | 把视频压缩成连续的视频码流，再按帧或按数据包传输。 |
| 编码质量参数 | 控制压缩程度的参数。 | 传统模式必须固定并记录，否则不同运行之间无法公平比较。 |
| 码流/载荷 | 编码后真正需要发送的数据。 | 统计数据量时要明确是否包含头部、分包信息和重传数据。 |
| 解码 | 把编码后的数据还原为图片或视频。 | 解码后的结果才可以计算 PSNR、SSIM 或进入任务模型。 |

> **初期建议：**
>
> 如果时间紧，先只做“单张图片 + JPEG + 端到端指标”。图片链路跑通后，再扩展到“视频 + H.264”和“SNR 多组对比”。

## 5. 传统通信和语义通信有什么不同

传统通信倾向于传输完整图片、视频或常规编码后的完整载荷；语义通信则尝试只传输完成任务所需要的语义、特征或关键内容。

| 对比项 | 传统通信 | 语义通信 |
|---|---|---|
| 发送端处理 | JPEG、H.264 等常规编码。 | 语义模型提取任务语义、特征或关键内容。 |
| 链路传输内容 | 完整图片、视频流或常规编码载荷。 | 语义载荷，必要时可附带关键帧、ROI 或残差。 |
| 接收端处理 | 常规解码，再输出内容或运行任务模型。 | 语义解码，再输出重建内容、结构化语义或任务结果。 |
| 要比较什么 | 通信开销、时延、重建质量、任务性能和计算资源。 | 同样记录这些指标，再看两种模式的差异。 |

> **公平比较的原则：**
>
> 两种模式必须使用同一个输入、同一个任务和同一条链路。基础对比保持链路条件一致；做 SNR 对比时，只调整 SNR，其他系统配置不变。不能预先假设语义通信一定提升多少，最终以现场实测数据为准。

## 6. 这些专有名词分别是什么意思

| 名词 | 简单解释 | 你为什么要关心 |
|---|---|---|
| 发送端 | 把信息发出去的设备或程序。 | 主演示中通常是 DGX Spark A。 |
| 接收端 | 接收信息并还原结果的设备或程序。 | 主演示中通常是 DGX Spark B。 |
| 链路 | 发送端和接收端之间传输数据的通道。 | 可能是 Wi-Fi、5G 或有线网络，由课题三提供。 |
| 数据包 | 网络传输中的小块数据。 | 大文件通常要拆包，接收端再重组。 |
| 载荷 | 数据包中真正有用的内容。 | 传统模式的图片/视频编码数据就是主要载荷。 |
| SNR | 信号与噪声的强弱比，常用 dB 表示。 | SNR 越低，通常代表信道条件越差，可能出现更多错误。 |
| 吞吐量 | 单位时间实际传输了多少数据，常用 Mbps 或 MB/s。 | 反映传输速度；视频还要看是否能稳定达到需要的帧率。 |
| 端到端时延 | 从任务启动到接收端形成最终结果所用的总时间。 | 这是 Demo 体验中最直观的指标之一。 |
| 丢包率 | 发送的数据包中没有成功到达的数据包比例。 | 丢包可能导致图片损坏、视频卡顿或重传。 |
| 误码率 | 收到的数据中发生比特错误的比例。 | 如果课题三能够提供，就一起记录。 |
| 帧率/FPS | 视频每秒处理或显示多少帧。 | 帧率下降通常会表现为视频不流畅。 |

## 7. 性能指标应该怎样理解

### 7.1 传输开销和数据量

传输开销就是为了完成一次任务，网络实际需要搬运多少数据。通常至少要记录“编码后载荷大小”和“实际传输总字节数”。如果统计口径不同，比较结果会失真。

- **单次任务总字节数：**一次图片或视频任务实际发送的总数据量。
- **平均吞吐：**一段统计时间内的平均传输速度。
- **峰值吞吐：**运行过程中出现的最高传输速度。
- **视频指标：**还应记录平均帧率、峰值帧率和丢帧数量。

### 7.2 端到端时延

端到端时延不是单纯的网络延迟。它可以包含编码、发送、网络传输、接收重组、解码和任务推理等时间。建议总时延之外，再记录各阶段耗时，方便定位瓶颈。

```text
端到端时延 = 结果形成时间 - 任务启动时间
```

### 7.3 重建质量指标

| 指标 | 大致含义 | 如何看 |
|---|---|---|
| PSNR | 衡量重建图片与原图的像素差异，单位通常是 dB。 | 一般数值越高，像素层面越接近原图。 |
| SSIM | 从亮度、对比度和结构等方面衡量图像相似性。 | 通常越接近 1 越相似。 |
| LPIPS | 用深度特征衡量感知上的相似程度。 | 通常越低越接近；是否使用由算法和联调决定。 |

注意：PSNR、SSIM 只适合有“原图”和“重建图”的场景。如果语义通信直接输出“识别结果”而没有重建图，就应该比较任务指标，而不是强行计算图像质量。

### 7.4 任务性能指标

如果 Demo 的目标不是还原图片，而是识别、检测或分类，那么最终任务结果更加重要。常见指标包括：

- **准确率：**预测正确的比例。
- **召回率：**真实目标中被找出来的比例。
- **F1：**综合准确率和召回率的指标。
- **mAP：**目标检测等任务常用的综合评价指标。
- **结果一致性：**两种通信方式最终任务结果是否一致。

### 7.5 计算状态

计算状态用于说明通信性能是用多少设备资源换来的。运行时记录 CPU/GPU 利用率、内存/显存占用和任务状态。不要只看 GPU 利用率，也要记录编码、解码和模型推理分别花了多少时间。

## 8. 你的实验应该怎么设计

实验的目标不是只跑出一组漂亮数字，而是让别人能够复现并相信这个比较。建议按下面顺序进行：

1. **固定样本：**先选定一张图片或一段视频，并记录文件名、大小、分辨率和时长。
2. **固定任务：**明确本轮是重建、分类、检测，还是其他任务。
3. **固定传统编码参数：**例如 JPEG 质量参数、H.264 码率或编码档位。
4. **固定链路：**使用同一对发送端和接收端、同一种链路以及同一统计窗口。
5. **先跑传统模式，再跑语义模式：**两次运行使用相同的输入、任务和链路条件。
6. **保存原始日志：**不要只保存最终平均值，要保留每次运行的明细。
7. **生成对比结果：**用表格展示单次结果，用折线图展示不同 SNR 下的变化。

### 数据量降幅公式

```text
数据量降幅 = （传统模式数据量 - 语义模式数据量）÷ 传统模式数据量
```

注意：两种模式必须采用同一种数据量统计口径。

## 9. 你需要编写的程序模块

| 模块 | 最低要求 | 产出 |
|---|---|---|
| 发送端 | 读取图片/视频，完成传统编码并调用传输接口。 | 编码后的载荷、发送时间、发送字节数。 |
| 接收端 | 接收数据、重组数据、完成传统解码。 | 重建图片/视频、解码状态和耗时。 |
| 任务处理 | 根据 Demo 任务决定是否运行后续任务模型。 | 准确率/召回率/F1/mAP 或结果一致性。 |
| 指标统计 | 统一记录通信、质量、任务和资源指标。 | JSON/CSV 原始记录和汇总结果。 |
| 配置管理 | 集中保存样本、编码参数、SNR 和任务设置。 | 可复现的配置文件。 |
| 联调接口 | 向课题一 Web 页面提供运行控制和结果查询。 | 运行编号、状态、结果和错误信息。 |

**推荐的最小日志字段：**

```text
run_id, mode, input_file, task, codec, snr, total_bytes, latency_ms, psnr, ssim, task_metric, cpu, gpu, memory, status
```

## 10. 两周工作计划

| 时间 | 目标 | 完成标志 |
|---|---|---|
| 第一周：跑通 | 确定接口；完成单张图片的 JPEG 编码、传输、解码；记录数据量、时延、PSNR/SSIM 和资源状态。 | 能在两台设备上完成一次传统通信并产生完整日志。 |
| 第二周：优化和扩展 | 加入视频/H.264 或多组 SNR；补充吞吐、帧率、丢包和任务指标；接入 Web 展示。 | 能与语义模式并列展示，且结果可以复核。 |

如果时间非常紧，优先级应为：

1. 单张图片传统链路
2. 完整日志
3. 公平对比
4. SNR 曲线
5. 视频扩展
6. 性能优化

## 11. 联调时必须确认的问题

下面这些信息在 Word 方案中被留给联调阶段确定。你可以把它们整理成第一次会议的确认清单：

- 正式使用哪些图片或视频样本？是否需要固定文件版本或校验值？
- 本轮任务是重建、分类、检测，还是其他任务？最终输出是什么？
- 传统模式具体使用 JPEG、H.264 还是其他编码？质量/码率参数是多少？
- 课题三的发送、接收和传输统计接口怎么调用？
- SNR 采用哪些取值？是否能够提供丢包率、误码率和重传数据？
- “总字节数”是否包含包头、协议头、重传和控制信息？
- 端到端时延从哪个时间点开始，到哪个结果形成时间结束？
- CPU/GPU、内存/显存状态由谁采集，采样周期是多少？
- Web 页面需要什么输入接口、结果字段和错误状态？

## 12. 最后用一句话检查自己是否做对了

> **验收自检：**
>
> 给我同一份输入、同一个任务、同一条链路和同一个 SNR，我能分别运行传统模式和语义模式；两次运行都会生成可追溯的运行编号、原始日志、最终结果和性能指标；结果能够被课题一的 Web 页面并列展示。做到这三点，传统通信基线就基本完成了。

## 附录：常见缩写速查

| 缩写 | 英文全称 | 中文理解 |
|---|---|---|
| SNR | Signal-to-Noise Ratio | 信噪比，表示信号相对噪声有多强。 |
| PSNR | Peak Signal-to-Noise Ratio | 峰值信噪比，常用于比较重建图像质量。 |
| SSIM | Structural Similarity Index Measure | 结构相似性，衡量图像结构是否相似。 |
| LPIPS | Learned Perceptual Image Patch Similarity | 基于深度特征的感知相似度指标。 |
| CPU | Central Processing Unit | 中央处理器，负责通用计算和控制。 |
| GPU | Graphics Processing Unit | 图形处理器，常用于并行计算和模型推理。 |
| FPS | Frames Per Second | 每秒帧数，视频流畅度的重要指标。 |
| ROI | Region of Interest | 感兴趣区域，例如图片中需要重点传输的区域。 |
