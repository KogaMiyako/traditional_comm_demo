# 内容2：传统通信双端对接说明

本文只说明内容2与课题三、课题一对接时需要理解和确认的通信过程、接口和指标，不重复介绍代码目录、安装方法和具体运行命令。

## 1. 内容2负责什么

内容2负责把图片、视频或文字转换成可传输的字节数据，交给通信链路发送；接收端拿到完整字节数据后，再按照原编码格式解码，形成重建文件或任务结果。

内容2不负责实现真实无线链路、通信硬件、SNR 模型和设备状态采集。真实链路由课题三提供，内容2通过统一的传输适配接口调用它。

## 2. 双端通信过程

```text
发送端
  选择样本和任务
      ↓
  JPEG/H.264/AV1/UTF-8 编码
      ↓
  得到编码载荷 bytes，并计算大小和 SHA-256
      ↓
  携带元数据调用传输接口
      ↓
  课题三通信链路
      ↓
接收端
  接收并重组完整 bytes
      ↓
  校验长度、序号和 SHA-256
      ↓
  按 codec/container 解码
      ↓
  生成图片、视频、文字或任务结果
      ↓
  返回通信、时延、质量和任务指标
```

一次运行必须使用唯一的 `run_id`。发送端和接收端通过这个编号关联同一次传输，不能只依赖文件名或时间戳。

编码和传输是两个独立步骤：编码器只负责产生内容字节，传输适配器只负责发送和接收字节。更换 TCP、UDP 或课题三真实链路时，不应修改图片/视频编码和结果统计的业务流程。

## 3. 双端需要交换的数据

### 3.1 发送端提交的运行信息

发送前至少提供以下运行上下文：

```json
{
  "run_id": "traditional-image-001",
  "mode": "traditional",
  "sample_id": "image_001",
  "task_id": "reconstruction",
  "media_type": "image",
  "codec": "jpeg",
  "container": "jpg",
  "snr_db": null
}
```

### 3.2 发送载荷元数据

调用传输接口时，除 `payload: bytes` 外，至少携带：

```json
{
  "run_id": "traditional-image-001",
  "mode": "traditional",
  "sample_id": "image_001",
  "task_id": "reconstruction",
  "codec": "jpeg",
  "container": "jpg",
  "payload_size": 345678,
  "expected_total_bytes": 345678,
  "sequence_id": 0,
  "sha256": "..."
}
```

大文件可以分片传输。此时需要额外明确总分片数、当前分片序号、分片大小和重组超时；如果课题三已经负责分片，内容2只提交完整 payload。

## 4. 传输接口约定

内容2当前通过 `TransportAdapter` 隔离临时 TCP 实现。课题三接入时，建议提供等价能力，不要求业务层知道底层是 TCP、UDP、Wi-Fi、5G 还是其他设备接口。

```python
health_check(link_config) -> dict
configure_link(link_config) -> dict
send_payload(run_context, payload, metadata) -> dict
receive_payload(run_context) -> tuple[bytes, dict]
close_link(run_id) -> dict
get_link_status(run_id) -> dict
get_transport_stats(run_id) -> dict
```

各接口职责如下：

| 接口 | 作用 |
|---|---|
| `health_check` | 检查链路、发送端和接收端是否可用 |
| `configure_link` | 设置节点、链路、SNR 或其他课题三配置 |
| `send_payload` | 发送编码后的字节数据和元数据 |
| `receive_payload` | 获取并返回本次运行的完整载荷和接收信息 |
| `close_link` | 结束本次运行并释放链路资源 |
| `get_link_status` | 查询链路当前状态、错误和连接信息 |
| `get_transport_stats` | 获取发送、接收、吞吐、丢包和重传等统计 |

### 4.1 发送接口返回结果

`send_payload` 至少应能返回：

```json
{
  "success": true,
  "run_id": "traditional-image-001",
  "sent_bytes": 345678,
  "transport_time_ms": 128.4,
  "throughput_mbps": 21.5,
  "packet_loss_rate": null,
  "retransmission_count": null,
  "error": null
}
```

### 4.2 接收接口返回结果

接收端至少应返回：

```json
{
  "success": true,
  "run_id": "traditional-image-001",
  "payload": "<bytes>",
  "received_bytes": 345678,
  "complete": true,
  "sha256_valid": true,
  "error": null
}
```

实际接口可以使用文件路径代替 `payload`，但必须能说明文件是否完整、字节数是否一致以及校验是否通过。

## 5. 接收端处理要求

接收端收到数据后按以下顺序处理：

1. 根据 `run_id` 找到本次运行。
2. 重组分片或读取完整载荷。
3. 校验总长度、分片序号和 SHA-256。
4. 根据 `codec` 和 `container` 选择解码器。
5. 保存解码输出，并记录解码是否成功。
6. 如配置了任务模型，将解码结果交给任务模块。
7. 写入本次运行的结果和指标。

如果校验失败或数据不完整，不应把文件直接当作正常结果；应返回结构化错误，例如 `incomplete_payload`、`checksum_mismatch` 或 `decode_failed`。

## 6. 内容2提供给课题一的控制接口

课题一的 Web 页面或上层控制程序需要能够调用以下生命周期接口：

```text
health_check()
prepare_run(config)
start_run(context) -> run_id
get_status(run_id)
cancel_run(run_id)
get_result(run_id)
get_error(run_id)
```

运行状态建议统一为：

```text
offline -> ready -> preparing -> running -> completing -> completed
                                             ├-> failed
                                             └-> cancelled
```

状态中至少要有：当前阶段、阶段耗时或进度、发送端状态、接收端状态、链路状态、错误信息和 `run_id`。

## 7. 必须记录的指标

每次运行都应保存原始指标，不能只在网页上显示最终平均值。

### 7.1 数据量和传输指标

| 指标 | 含义 |
|---|---|
| `input_bytes` | 原始输入文件大小 |
| `encoded_payload_bytes` | JPEG、H.264、AV1 或 UTF-8 编码后的业务载荷大小 |
| `actual_sent_bytes` | 发送端实际发送的业务字节数 |
| `actual_received_bytes` | 接收端实际收到的业务字节数 |
| `actual_link_total_bytes` | 包含协议头、分片头、控制信息和重传数据的链路总字节数 |
| `average_throughput_mbps` | 本次传输的平均吞吐 |
| `peak_throughput_mbps` | 本次传输的峰值吞吐 |
| `video_fps` | 视频平均或峰值帧率 |
| `video_dropped_frames` | 视频丢帧数 |

必须区分 `encoded_payload_bytes` 和 `actual_link_total_bytes`，并在指标说明中注明是否包含协议开销和重传数据。

### 7.2 时延指标

建议记录以下时间点：任务启动、编码开始/结束、发送开始/结束、接收开始/结束、解码开始/结束、任务处理开始/结束、结果形成。

核心指标：

| 指标 | 定义 |
|---|---|
| `encode_time_ms` | 编码耗时 |
| `transport_time_ms` | 发送、接收及传输确认耗时 |
| `decode_time_ms` | 解码耗时 |
| `task_time_ms` | 任务模型处理耗时 |
| `end_to_end_latency_ms` | `结果形成时间 - 任务启动时间` |

### 7.3 信道指标

由课题三能够提供时记录：

```text
snr_db
packet_loss_rate
bit_error_rate
retransmission_count
```

如果某项暂时无法提供，应填 `null`，不要填入猜测值。

### 7.4 质量、任务和资源指标

- 重建类任务：`PSNR`、`SSIM`，需要时增加 `LPIPS`。
- 识别或检测类任务：`accuracy`、`recall`、`F1`、`mAP` 或结果一致性。
- 资源状态：发送端/接收端 CPU、GPU、内存、显存，以及设备和链路状态。

没有重建图片或视频时，不要强行计算 PSNR/SSIM；没有任务模型时，任务指标可以为 `null`。

## 8. 结果关联和存储

发送端和接收端的结果至少要通过以下字段关联：

```text
run_id + mode + sample_id + task_id + link_condition
```

每次运行建议保留：

```text
runs/<run_id>/
  config.json       # 输入、任务、编码和链路配置
  events.jsonl      # 各阶段时间和状态事件
  transport.json    # 课题三返回的传输统计
  metrics.json      # 指标汇总
  output.*          # 重建文件或任务结果
  error.json        # 失败时的结构化错误
```

接收端至少需要能提供：接收文件、解码输出、`receiver_result.json`。对接时不要求双方目录名称完全相同，但字段含义必须一致。

## 9. 明天需要和课题三确认的问题

1. 真实链路的发送和接收接口形式是什么：Python 函数、Socket、命令行还是服务接口？
2. 接收端是主动拉取、回调通知，还是由发送接口同步返回？
3. 课题三是否负责分片、重组、校验、乱序和重传？内容2提交的是完整载荷还是单个分片？
4. 如何配置和读取 SNR？能否返回实际 SNR，而不是只返回目标值？
5. 能否提供实际发送字节数、接收字节数、吞吐、丢包率、误码率和重传次数？
6. 传输统计是否包含协议头、控制信息和重传数据？
7. 链路断开、超时、接收不完整和校验失败分别如何表示？
8. 发送端、接收端、设备和链路的 ID 如何获取？

## 10. 对接验收标准

- 相同 `run_id` 能在发送端和接收端找到对应记录。
- 接收端能判断数据完整性，并明确区分传输失败、校验失败和解码失败。
- 不修改编码和业务流程即可替换课题三传输适配器。
- 能取得双方约定的数据量、吞吐、时延、信道和质量/任务指标。
- 传统通信和语义通信使用相同的运行编号、配置字段和结果字段，后续可以直接对比。
- 对暂时不可用的指标使用 `null`，并保留错误和状态信息。
