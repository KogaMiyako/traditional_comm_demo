# 传统通信代码预留接口与任务清单

## 这份文件解决什么问题

重新核对 Word 方案后，可以确定：你的代码不是只写“图片/视频编码”就结束了。后续要和课题一、课题三以及语义通信联调，所以必须提前把控制接口、传输接口、指标字段、状态字段和结果格式留出来。

最核心的目标是：

```text
同一输入 + 同一任务 + 同一链路条件
    -> 传统通信运行
    -> 语义通信运行
    -> 用统一格式比较结果
```

## 一、先区分责任边界

| 部分 | 负责什么 | 你的代码需要怎样配合 |
|---|---|---|
| 内容2 | 传统通信模型搭建和性能记录 | 实现常规编解码、传输适配、解码、指标和结果输出 |
| 课题一 | 任务控制、SNMP/状态采集、Web 页面、总体联调 | 提供可调用的控制、状态、结果接口 |
| 课题二 | 语义算法、模型、知识库、语义载荷 | 通过统一输入输出和结果格式参与对比 |
| 课题三 | 通信硬件、链路接入、数据收发、SNR、传输统计 | 使用抽象传输接口，不把 TCP/UDP 或硬件写死 |
| 课题四 | 演示验证和后续平台接口 | 保留验证记录和外部平台所需接口 |

主演示是两台 DGX Spark：一台发送、一台接收；第三台是备用设备，不属于必选链路。后续如果需要多跳或边缘处理，才扩展转发节点。

## 二、必须预留的九类内容

### 1. 任务和样本配置

Word 方案没有固定最终业务场景，样本、任务输出和 SNR 由联调确定。因此代码不能把任务、样本和输出形式写死。

需要配置：

- 图片或视频样本
- 样本 ID、路径、格式、校验值
- 图片分辨率或视频分辨率、时长、帧率
- 任务类型
- 输出类型：重建内容、结构化结果或任务结果
- 通信模式：传统或语义
- 编码格式和编码参数
- 链路类型和 SNR

建议统一配置对象：

```yaml
sample_id: ""
input_path: ""
media_type: image  # image / video
task_id: ""
task_type: ""
output_type: reconstruction
mode: traditional
codec: jpeg
codec_params: {}
link_type: ""
snr_db: null
```

### 2. 统一运行编号和生命周期

Word 方案要求每次运行使用独立编号，并保存输入配置、通信模式、SNR、任务结果和系统状态。

需要预留：

- `run_id`
- 运行开始、结束和失败时间
- `prepare`
- `start`
- `running`
- `completed`
- `failed`
- `cancelled`
- 状态查询
- 运行取消
- 错误查询
- 结果查询

建议状态流程：

```text
检查在线 -> 准备运行 -> 编码/发送 -> 接收/解码 -> 任务处理 -> 保存结果 -> 完成
```

### 3. 传统编解码接口

Word 方案的传统通信发送端要支持 JPEG、H.264 等常规编码；接收端要支持常规解码，并根据任务输出重建内容或运行任务模型。

代码需要把“编码器”独立出来，至少预留：

- 图片编码
- 视频编码
- 编码格式切换
- 编码质量、码率、分辨率、帧率参数
- 编码器版本
- 编码耗时
- 编码后字节数
- 解码耗时
- 解码失败信息

编码后的文件或载荷最终都会变成二进制字节数据，传输模块只接收字节，不需要理解 JPEG、H.264 或 AV1 的内部细节。

### 4. 课题三传输接口

Word 方案明确要求统一课题三提供的数据收发入口、SNR 设置方式和传输统计结果。

因此至少要预留：

```text
check_link()
configure_link()
send_payload()
receive_payload()
close_link()
get_link_status()
get_transport_stats()
```

发送时需要传递：

- `run_id`
- 数据模式
- 样本 ID
- 任务 ID
- 编码格式
- 编码后的字节数据
- 分包序号或数据序号
- 数据总长度

接收后需要拿到：

- 是否成功
- 是否完整重组
- 实际发送字节数
- 实际接收字节数
- 平均吞吐
- 峰值吞吐
- 传输时延
- SNR
- 丢包率、误码率、重传次数（如果课题三能提供）

不要在内容2业务代码里直接假设一定使用 TCP 或 UDP。TCP/UDP 只是传输层协议，最终使用哪种方法由课题三接口决定。没有真实接口时，可以用本地 TCP 做临时测试适配器。

### 5. 任务结果接口

Word 方案允许不同类型的输出，因此接收端不能只返回一个视频文件。

需要支持：

- 重建图片
- 重建视频
- 结构化语义结果
- 分类/检测等任务结果
- 任务模型推理耗时
- 模型版本
- 结果一致性

传统通信侧可能是：

```text
常规解码 -> 重建图片/视频
常规解码 -> 同一个任务模型 -> 任务结果
```

### 6. 性能记录接口

Word 方案要求记录以下指标。

#### 传输开销

- 单次任务总字节数
- 编码载荷字节数
- 平均吞吐
- 峰值吞吐
- 视频平均帧率
- 视频峰值帧率
- 视频丢帧数

#### 端到端时延

需要记录：

- 任务启动时间
- 编码耗时
- 发送耗时
- 网络传输耗时
- 接收重组耗时
- 解码耗时
- 任务推理耗时
- 最终结果形成时间
- 端到端总时延

统一公式：

```text
端到端时延 = 接收端形成最终结果的时间 - 任务启动时间
```

#### 重建质量

- PSNR
- SSIM
- LPIPS（需要时）

如果只有任务结果、没有重建图片或视频，就不应该强行计算 PSNR/SSIM，而应使用任务指标。

#### 任务性能

- 准确率
- 召回率
- F1
- mAP
- 结果一致性

#### 信道条件

- SNR
- 丢包率
- 误码率
- 重传次数

其中丢包率、误码率和重传次数取决于课题三是否提供。

#### 计算状态

- 发送端 CPU 利用率
- 接收端 CPU 利用率
- 发送端 GPU 利用率
- 接收端 GPU 利用率
- 内存占用
- 显存占用
- 任务运行状态
- 链路运行状态
- 设备在线状态

#### 派生指标

数据量降幅：

```text
（传统模式数据量 - 语义模式数据量）÷ 传统模式数据量
```

SNR 对比还要保存：

- 预定 SNR 序列
- 每个 SNR 下的传统模式结果
- 每个 SNR 下的语义模式结果
- 重建质量或任务性能曲线数据
- 每个 SNR 下的数据量和端到端时延

### 7. Web 页面接口

Web 页面至少包含四个区域，虽然页面由课题一负责，但你的代码必须提供数据。

#### 任务控制

- 选择样本
- 选择任务
- 选择输出类型
- 选择通信模式
- 设置编码参数
- 设置链路条件
- 启动/停止/重试
- 显示当前运行编号

#### 拓扑视图

- 节点 ID
- 发送端/接收端/备用/转发角色
- 在线状态
- 节点之间的链路状态
- 链路类型

#### 节点详情

点击节点后，至少应能显示：

- 设备状态
- 当前模型版本
- 知识库版本
- 当前运行编号
- CPU/GPU 利用率
- 内存/显存占用
- 操作系统
- CPU/GPU 架构
- 驱动、CUDA、TensorRT、深度学习框架版本
- 当前任务状态

#### 链路详情

点击链路后，至少应能显示：

- SNR
- 吞吐
- 累计传输量
- 丢包率/误码率（可用时）
- 链路状态

#### 结果对比

- 传统运行编号
- 语义运行编号
- 相同输入和任务配置
- 数据量
- 吞吐
- 端到端时延
- 图像/视频质量
- 任务性能
- 计算资源状态

### 8. 设备和软件环境信息

主演示设备是两台 DGX Spark，第三台备用。Word 方案还说明 DGX Spark 是 ARM64，RTX 主机通常是 x86_64，因此要给代码留环境信息字段。

需要记录：

- 设备名称和节点角色
- 操作系统版本
- CPU/GPU 架构
- NVIDIA 驱动版本
- CUDA 版本
- cuDNN 版本
- TensorRT 版本
- 深度学习框架版本
- FFmpeg/GStreamer 版本
- 编解码器是否可用
- 模型版本
- 知识库版本

如果同一程序需要跑在 DGX Spark 和 RTX 主机上，要准备分架构软件包或多架构容器镜像。

### 9. 结果文件和原始日志

建议每次运行都单独保存：

```text
runs/<run_id>/
  config.json
  transport_stats.json
  metrics.json
  resource_samples.jsonl
  events.jsonl
  encoded_payload.*
  reconstructed_output.*
  task_result.json
  error.json
```

至少要能根据以下字段关联传统模式和语义模式：

```text
run_id
sample_id
task_id
mode
snr
link_type
```

## 三、SNR 对比必须怎么留接口

SNR 对比时，代码需要接收一个 SNR 数组，而不是把某个数值写死：

```yaml
snr_sweep:
  enabled: true
  values_db: []
```

对每一个 SNR，分别运行传统模式和语义模式。除 SNR 外，以下内容都必须保持一致：

- 样本
- 任务
- 编码参数
- 节点角色
- 模型和软件配置
- 统计窗口
- 指标口径

## 四、最终建议的代码结构

代码不需要很大，但建议保留这些模块边界：

```text
config              # 配置和运行上下文
run_control         # 现场控制和生命周期
codec_adapter       # JPEG/H.264/AV1 编解码
transport_adapter   # 课题三链路接口
task_adapter        # 任务输出和模型调用
metrics             # 指标计算
state_collector     # 设备/链路/任务状态
result_store        # 运行目录、日志、输出文件
comparison          # 两种模式和 SNR 对比
web_adapter         # 课题一页面接口
```

第一版可以只实现：

```text
config + codec_adapter + 临时TCP transport_adapter + metrics + result_store
```

接入课题三后，只替换 `transport_adapter`，不要重写整个程序。

## 五、按 Word 现场流程检查是否留全

程序最终应该能支持：

1. 检查两台 DGX Spark、课题三链路和状态服务是否在线。
2. 选择图片/视频样本、任务输出和链路条件。
3. 启动传统通信并保存结果、传输开销、时延和节点计算状态。
4. 保持输入、任务和链路条件一致，启动语义通信。
5. 用相同格式并列展示两次运行。
6. 如做 SNR 对比，按预定 SNR 序列重复两种模式并生成曲线。

## 六、最重要的验收标准

只要做到下面几点，接口预留就基本完整：

- 更换 JPEG/H.264/AV1 时不需要重写传输代码。
- 更换 TCP/UDP/课题三链路时不需要重写编码代码。
- 每次运行都有唯一 `run_id`。
- 输入、任务、模式、SNR、链路和软件环境可追溯。
- 传统和语义通信使用同一输入、任务、链路条件和结果格式。
- 图片、视频、重建结果和任务结果都能表达。
- 性能记录包含数据量、吞吐、时延、质量/任务指标、信道和资源状态。
- Web 页面需要的任务、拓扑、节点、链路和对比字段都有查询入口。
- 失败、取消、超时和链路断开都有明确状态和错误信息。
